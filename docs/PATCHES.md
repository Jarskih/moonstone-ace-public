# Adding a patch (and the integrator workflow)

Patches rewrite lines of the reassembled original asm so a routine is replaced by a call into C++.
`asm/*.s`, `asm/synth.s`, `include/rt/abs.h`, `src/rt/abs_stubs.cpp` are generated by
`tools/resource.py`; never hand-edit them. **Since ROADMAP 7.1r no asm is linked** (see the last section): `asm/{program,mog}.s` and the patch tables are the
reference listing that `--verify` proves load-equivalent to the original, plus the source of `asm/synth.s` (MS_SYNTH_ASM). Hint for agents: a new area needs only **new files**
(a patch file + C++), never an edit to `abs_symbols.json`.

## Patch file

`asm/patches/<bin>.<area>.json` (`<bin>` = `program` or `mog`; one owner per area; ids unique across all files):

```json
{
 "binary": "mog",
 "funcs": [ {"name": "rt_area_do", "impl": "src/rt/area.cpp"} ],
 "constants": { "rt_area_flag": "0x1234" },
 "patches": [
  { "id": "area-do", "line": 8256, "orig": ["\tLEA\tLAB_05B9,A2"], "new": ["\tJMP\trt_area_do"], "why": "..." }
 ]
}
```

- `patches`: as before (`line`/`orig`/`new`, or `kind: as_data`); `orig` must match the original listing text.
- `funcs` (optional): rt_* functions the patch calls. `impl` names the C++ file that defines
  `extern "C" void rt_area_do(void)`. The generator declares them in `abs.h` (comment = impl path)
  and emits no stub. Without a `funcs` entry the verify build fails with
  `rt_x is not in abs_symbols.json or a patch-local "funcs" table`.
- `constants` (optional): extra absolute values (verify build) for names the patches use.
- Merged with `abs_symbols.json`'s `funcs`/`constants`: the same name with the same `impl` in two files is fine;
  a different `impl` (or constant value) raises `PatchError` naming both files. Existing numbering of the
  `abs_symbols.json` functions is unchanged; patch-local ones are appended in file-name order
  (their pseudo-address `0xF80000 + 0x10*index` only matters inside the verify build).
- Definitions in C++ must be `extern "C"` and the file must be globbed by CMake (`src/**/*.cpp` is).
  Add a bare data symbol/RAM cell (`rt_*` variable) to `abs_symbols.json` `symbols` as before.

## Workflow

```sh
py tools/integrate.py                       # regenerate, verify, build + hdinstall, auto-selected tests
py tools/integrate.py --tests none --skip-build   # just regenerate + verify
py tools/integrate.py --boot "wait:40,shot:integ" # then boot it and take a screenshot (needs the desktop: sends keys)
py tools/integrate.py --boot                       # + build-autoplay/, then the headless autoplay boot regression (tests/boot/,
                                                   #   docs/AUTOPLAY.md): PASS/FAIL per screen vs build/shots/ref/; no keys, no focus
py tools/integrate.py --boot --only-boot           # only the boot, builds as they are
```

Gates, in order: `resource.py`, `resource.py --verify --no-write` (prints, per binary, that all differences
lie inside N patch ranges), `cmake --build` of `build/`, `build-game-debug/`, target `hdinstall`, then tests.
`--tests auto` runs `tests/test_*.py` whose source text mentions a file changed vs HEAD (diff + untracked;
files owned by the lifting session are ignored: `src/lifted/**`, `tools/lift*.py`, `tools/diffharness/**`,
`tools/symbols.yaml`) plus `test_resource`. Full logs: `build/integrate/*.log`. No commit logic.
The script sets the toolchain PATH itself.

## Bisecting a boot regression

```sh
py tools/bisect_patches.py --disable mog.loaders.json --disable-id cl-select --steps "wait:40,shot:x" --shot bis1
```

Backs `asm/patches/` up to `build/bisect_backup/`, drops the named patches (whole file, or ids), regenerates,
builds `hdinstall`, boots with `uaeshot.ps1 -Joy -Steps ...`, and always restores the tables and regenerates
in a `finally` (a stale backup of a killed run is restored on the next start). `--build-only` skips the boot.
A disabled patch's `funcs` stay, so symbols still resolve; its C++ is then simply unused.

## Working in a worktree

```sh
py tools/worktree_setup.py --path D:/Amiga/wt/display --branch wt-display   # from the main checkout
cd D:/Amiga/wt/display/moonstone-ace && py tools/integrate.py
# or, inside an already created worktree:
py tools/worktree_setup.py --here
```

It junctions the git-ignored inputs from the main checkout (`build/{disks,reasm,inventory,art}`, `reference/`,
`tests/diff`, `tools/{toolchain,AmigaCMakeCrossToolchains,bartman_gcc_support}`) and configures the worktree's own
`build/` (Release) and `build-game-debug/` (Debug), both the game, from the main checkout's CMake cache. The
junctions are shared: do not write into them. `build-debug/` is not configured (use BUILD.md). Remove a worktree by
deleting the junctions with `rmdir`, then `git worktree remove`. `moonstone-ace-hd.uae` mounts the MAIN checkout's `build-game-debug/hd`; to boot a worktree build, copy that config and
change the `filesystem2=` path to the worktree's `build-game-debug\hd` (and do not boot two at once).

## Boot regression after a patch

`--boot` (no value) is the one-command check that a patch did not break the boot path menu -> knight select -> name entry -> map and
menu -> Practice -> walk. It builds `build-autoplay/` (Debug, `-DMS_AUTOPLAY=ON`; configured automatically from
`build-game-debug`'s cache) and drives the game with injected input, so it runs unattended and beside other WinUAEs (instance 3).
After an intended visual change re-promote the affected references: `py tools/shotcmp.py <shot> --promote`. In a worktree the references
are the worktree's own `build/shots/ref/` (copy them from the main checkout, `build/` is not shared except the junctions listed above).
`worktree_setup.py` now also works with a forward-slash `--path` (mklink needs backslashes).

## C++-owned DATA/BSS hunks (`extern_data`, ROADMAP 7.1n1)

`asm/patches/<bin>.data.json` (`binary`, `patches: []`, `extern_data`) names DATA/BSS hunks whose cells C++ owns:

```json
{"binary": "program", "patches": [], "extern_data": [ {"section": 16, "object": "g_ioFlags", "type": "IoFlags"} ]}
{"binary": "mog",     "patches": [], "extern_data": [ {"section": 21, "object": "g_mogIoFlags", "twin_of": "program:16"},
                                                      {"section": 22, "object": "g_ioKeys", "twin_of": "program:17", "share": true} ]}
```

- `tools/gen_data.py` (CMake runs it, output `build/gen/owned_data.{hpp,cpp}`, git-ignored: the contents come from the
  original asm) emits one packed `ms::owned::<type>` struct per hunk (a member per label run, typed by the asm cell width, a
  pointer cell is a `const char *` link-time constant) and an `extern "C"` object `<object>` initialised with the DC data (BSS: zero).
  A top-level asm block in the same file (compiled `-fno-lto`) defines the cells' names as `.set mogCurKnight, g_mogState+0x278` (the C++ names of
  `tools/cell_names.yaml`, ROADMAP 7.1s) and, only where a source still spells the label, `.set prg_LAB_0362, g_ioFlags+1` (one copy, no vasm object any more).
  A linker-script assignment instead would make the aliases absolute symbols, which elf2hunk cannot relocate.
- `tools/resource.py` leaves the hunk out of the **elf** asm (`XREF` instead of `XDEF` for its labels); the verify build keeps
  it, so `--verify` stays load-equivalent. A patch inside an owned hunk is an error.
- `twin_of`: re-use the struct type of that entry (the hunk must be byte-congruent, pointer cells compared by position) with
  its own object, because a pointer cell points into its own binary's code. `share: true` (no pointer cells, zero-initialised only):
  the twin's labels alias the base object, one copy for both overlays.
- Overlay re-entry: the generated reset tables (`rt::g_imageProgram` / `g_imageMog`, 7.1r) snapshot/restore/zero by object + size exactly as `image_tab` did, so the owned objects are
  re-initialised at each entry. An owned DATA hunk of only zero cells is listed as BSS there (same reset; keeps shared twins right).
- CHIP hunks are refused for now (7.1n4). Proof: `tests/test_gen_data.py` compiles the generated file with m68k g++ and compares
  object bytes, pointer relocations and label aliases against the original binaries.

### Area files and typed members (ROADMAP 7.1n3)
- `gen_data.py` reads every `asm/patches/<bin>.data*.json` (`mog.data.json`, `mog.data_state.json`, ...), one owner per area;
  a section named twice is an error. CMake globs `*.data*.json`.
- An entry may carry `"includes": ["game/state.hpp"]` and `"typed": [{"label", "through"?, "name", "type" | "ptr", "count"?}]`:
  the zero-initialised label runs from `label` to the end of `through` become ONE member of that C type (`ptr`: pointer cells
  to it). The header static_asserts `sizeof(type) * count` and every member's `offsetof` against the original label offsets.
  Example: `mog.data_state.json` (S_1 -> `ms::owned::GameState g_mogState`; `mog_LAB_0613` etc. stay as `.set` aliases).

### CHIP hunks (ROADMAP 7.1n4)

`{program,mog}.data_chip.json` own the CHIP DATA/BSS hunks (program S_27/S_30, mog S_15/S_32/S_35/S_43). The generated objects live in
`.chipdata.MEMF_CHIP` (DATA, via `section(...)`) or `.chipbss.MEMF_CHIP` (BSS, defined in the file's asm block with `@nobits`: a
GCC `section()` attribute would make it PROGBITS and put the zeros in the exe); elf2hunk maps sections ending `.MEMF_CHIP` to
MEMF_CHIP hunks (`tests/test_gen_data.py` `ChipData` parses the exe's HUNK_HEADER). `"names"` / `"widths"` give label-run members
readable names / u16 cells; a cell a patch points at an `rt_*` symbol (the display screen cells) is a link-time constant.
mog S_32 `share`s program S_27's object (zero BSS, byte-congruent): one 45,744-byte chip copy instead of two.

## No asm in the link (ROADMAP 7.1r)

The game executable contains no vasm object. What replaced the asm, and what is left of it:

- **Entries.** `rtGameRun` (src/rt/game.cpp) calls `rt_prg_main` (progmain.cpp) and `rt_mog_entry` (the audio quiesce, then `rt_mog_main`) directly.
- **Code-hunk data cells** (`asm/patches/<bin>.data_cells.json`, `"extern_cells": [{"label": "LAB_0122"}]`, optional `"size"`): a flag word, text or table
  that lay inside a CODE hunk and that C++ reads or writes. gen_data makes it the object `g_cell_<prefix><label>`, initialised from the ORIGINAL binary at the
  label's hunk offset (the extent is the distance to the next label of the hunk; a relocated longword is a pointer cell), and aliases the label to it like the
  hunk objects. Cells are not part of the overlay-entry reset (they never were). To add one: list it, rebuild; `tests/test_gen_data.py` (`cell_diffs`) compares
  every cell with the original binary.
- **`"link_names": {"LAB_0360": "rtNoop", "LAB_003F": "rtScnFlash"}`**: a pointer cell in owned data that held the address of a code label (an RTS default, an
  animation-script callback) holds that C++ function instead (src/rt/noop.cpp, src/rt/engine_scenes.cpp).
- **`"asm_labels"`**: labels only the optional synth hunk defines; the S_45 pointer cells naming them are `nullptr` unless gen_data runs with `--asm-labels`.
- **Overlay-entry reset**: `rt::g_imageProgram` / `rt::g_imageMog` are generated into the same file (see the re-entry paragraph above).
- **MS_SYNTH_ASM** (A/B listening, owner has not signed off on the C++ synth): `asm/synth.s` is mog's S_44 alone (`resource.py` `write_synth`, labels of every other hunk
  XREF, `LAB_0FC4` is the C++ cell `g_cell_mog_LAB_0FC4`); CMake assembles it with vasm and generates the data with `--asm-labels`. It is the only asm that can be linked.
- ROADMAP 7.1s: `tools/cell_names.yaml` gives the cells C++ names (`mogCurKnight` instead of `mog_LAB_0633`; `py tools/rename_cells.py --apply` rewrites the sources, `--check`/`--left` say what is left);
  gen_data defines the alias under the new name and keeps a `prg_LAB_xxxx` alias only for labels the sources, a pointer cell or `asm/synth.s` still spell. The unicorn
  tests resolve the names back to labels with `tools/cellnames.py` (`legacy`, `defsym_aliases`).
- `build/gen` is now `<build dir>/gen` (the synth build generates different pointer cells). The thunk machinery (`tools/thunks.py`, `resource.py --swap-list`,
  `MS_SWAP_LIST`, `src/rt/thunks.cpp`, `src/rt/gen/hunk_tab.cpp`, `include/ms/linked.hpp`) is retired from the build: it swapped lifted bodies into asm.
  `MS_LINK_LIFTED` stays as a cross-compile check of `src/lifted/**`.
